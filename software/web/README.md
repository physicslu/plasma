# Plasma PPU Console

React/TypeScript Web Console for one Plasma Programming Unit (PPU). The UI discovers PPU identity and Site topology from the canonical REST status contract, submits one-based Site jobs to the Plasma Web REST Gateway, polls real job/Site state, and sends cancel requests to the backend. Progress is not generated by a browser timer.

## Runtime path

```text
Browser / Plasma PPU Console
        |
        | HTTP REST polling
        v
Plasma Web REST Gateway
        |
        | Plasma Protocol v3.2 / PLASMA32
        v
Plasma Server
        |
        v
SiteManager / SiteWorker
```

Canonical identity is:

```text
SITE 1 -> site_id = 1
SITE 2 -> site_id = 2
...
SITE N -> site_id = N
```

The current prototype configuration normally enables SITE 1 and SITE 2. Additional Sites remain disabled or absent according to the PPU-reported topology; the Web Console must not hard-code an eight-Site device assumption.

## Requirements

- Node.js version satisfying `package.json` (`>=22.13.0` at the current baseline)
- Plasma Server and Plasma Web REST Gateway from `../python`

The current Gateway is implemented with Python standard-library `ThreadingHTTPServer`. It is not FastAPI and does not use WebSocket.

## Run locally

Start the Python processes first:

```bash
cd ../python
python -m plasma_server.server --config config/plasma.yaml
python -m plasma_web.gateway --host 127.0.0.1 --port 8080
```

Then start the UI in another terminal:

```bash
npm run install:ci
npm run dev
```

The code-level local Gateway port shown above is not the integration-host deployment source of truth. Deployment values are generated by `scripts/plasmactl` and its persistent deployment configuration.

The default deployed API Base is supplied through `NEXT_PUBLIC_PLASMA_API_URL`. An operator may override the API Base for development, but browser storage must not become authoritative for PPU inventory or Site capability.

For a shared LAN, bind the Gateway intentionally and restrict CORS to the expected Web origin. CORS is not authentication; do not expose this prototype Gateway directly to an untrusted network without an explicit security design.

## Job behavior

- Canonical Web requests send one-based `site_id` only.
- `program` means write only; a full programming flow is composed by the client as `erase -> program -> verify` when selected.
- Batch operation checkboxes may select any subset of Erase / Program / Verify / Read.
- Selected Sites execute independently/concurrently; one Site must not wait for an unrelated Site unless a real shared resource requires synchronization.
- Per-Site cancellation must not cancel unrelated Sites.
- Protocol v3.1 read compatibility may still be tested at explicit compatibility boundaries, but new Web write requests must not dual-send `channel_id`.

## Checks

```bash
npm run lint
npm test
npm run validate:artifact
```

Browser-level validation lives under `e2e/` and includes Playwright functional tests plus deterministic Visual Regression scenarios. A Visual Regression baseline is a fixed CI artifact, distinct from an operator-provided live runtime screenshot used as a design/reference baseline.
